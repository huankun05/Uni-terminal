# 设计文档 01 · 长期凭据、传输与手机端 UI 架构

> 项目：Uni-terminal（统一 AI Coding Agent 终端控制台）
> 定位：自用 + 开源（MIT）
> 本文回答：如何做到「一次配对、长期有效」，同时不牺牲安全性与便利性；底层在什么基础上改；手机端 UI 如何设计。

---

## 0. 先把问题对准

「长期有效」这四个字，真正的难点不是「怎么让 token 不过期」—— 那是 5 行代码的事。难点在于：

> **一旦把凭据寿命拉长，凭据泄露 = 永久失守。**

ZCode 就是踩了这个坑：它的远控**连接链接本身就是授权**，拿到链接即拿到全部操作权限，没有有效期、没有吊销机制。它用「短命」换「安全」，代价是难用；而如果它直接把链接做成长期有效，那就变成「永久后门」。

所以真正要解的题是：

| 目标 | 冲突 | 解法方向 |
|---|---|---|
| 长期有效（不要反复扫码） | 泄露风险随时间累积 | 寿命长的凭据必须**可以被吊销**、且**只能换取短命凭据** |
| 安全 | 便利性 | 凭据分层：长命的只做身份，短命的做操作 |
| 便利 | 安全 | 设备侧生物识别（Passkey）替代「记密码/每次扫码」 |

**一句话结论：长寿命只给「身份凭据」，绝不给「会话凭据」；身份凭据必须可吊销、且与设备硬件绑定。**

## 1. 核心设计：三层凭据模型

这是整个方案的骨架。

| 层 | 名称 | 寿命 | 存储位置 | 泄露后影响 | 失效方式 |
|---|---|---|---|---|---|
| **L1** | 配对码 Pairing Code | **5 分钟 / 单次** | 服务端内存 | 几乎为零（已被消费或已超时） | 用完即焚 / 超时自毁 |
| **L2** | 设备凭据 Device Credential | **长期**（滑动续期，默认 180 天） | 服务端下发的 **httpOnly Cookie** | 需配合 TLS 破解或物理接触设备；**可一键吊销，立即生效** | 服务端设备表删除 → 立刻失效 + WebSocket 踢线 |
| **L3** | 会话凭据 Access Token | **15 分钟** | 浏览器内存（JS 变量，**不落盘**） | 15 分钟后自动作废，且**换不到 L2** | 自然过期 |

### 1.1 时序：首次配对（只做一次）

```
桌面端（已登录，可信）          服务端                    手机（未可信新设备）
   │                             │                              │
   │ ① 点「添加设备」             │                              │
   │ ② POST /pair/new ──────────►│                              │
   │ ◄── pairId + 一次性签名 challenge                           │
   │                             │                              │
   │ ③ 屏幕显示二维码（含 pairId）│                              │
   │                             │                              │
   │                             │      ④ 用户用手机扫码 ◄───────│
   │                             │         （打开 PWA，带上 pairId）
   │                             │ ◄── ⑤ 手机登记自己的公钥 ────│
   │                             │                              │
   │ ◄── ⑥ 推送「有新设备请求接入」│                              │
   │     显示：iPhone 15 · Safari · 来自 192.168.x.x             │
   │ ⑦ 用户点「允许」← 授权发生在可信设备上                       │
   │ ── ⑧ 批准（附带账户密钥，用手机公钥加密后交服务端）─────────►│
   │                             │                              │
   │                             │ ── ⑨ 下发加密载荷 + L2 凭据 ►│
   │                             │        ⑩ 手机用私钥解密       │
   │                             │          （服务端全程看不到明文）
   │                             │        ⑪ 引导创建 Passkey     │
   │                             │        ⑫ 进入控制台，此后免扫码
```

**三个关键设计点**：

1. **二维码不是凭据，只是 pairId。** 它只负责「把手机和服务端牵上线」。真正的授权是第 ⑦ 步那一下人工点击。所以即使二维码被偷拍到，攻击者扫了之后桌面端会弹窗显示陌生的设备信息（UA、来源 IP），你看到就能拒绝。

2. **授权动作必须发生在可信设备（桌面端）上。** 手机是未可信的新设备，它只能「请求」；桌面端（已在你手里、已登录）才是「批准方」。**这正是 ZCode 的坑** —— 它「扫码即授权」，二维码本身等于万能钥匙。

3. **扫码方向选「手机扫桌面」，因为台式机通常没有摄像头。** 注意区分两件事：**扫的是手机相机，批准的是桌面端**。授权方向不变（仍在可信设备），只是不用桌面端的摄像头。
   - 如果桌面端是纯 CLI 无图形界面：在终端打印二维码（ASCII 或图片），批准时终端输入 `y/N`。功能等价，很多 CLI 工具都是这个做法。

### 1.2 时序：日常打开（长期有效的路径，零扫码）

```
手机 PWA                              服务端
   │                                    │
   │ ① 打开 PWA（已装到主屏幕）          │
   │ ② 浏览器自动带上 L2 httpOnly Cookie►│
   │                                    │ ← 校验设备表：存在且未吊销？
   │ ◄── 200 { L3 accessToken(15min) }  │
   │ ③ 内存持有 L3，建立 WebSocket        │
   │ ④ 正常使用                          │
   │ ⑤ L3 到期前静默续期（用 L2 换新的 L3）│
   │ ⑥ Cookie Max-Age 滑动刷新           │
   └────────────────────────────────────┘
```

### 1.3 时序：凭据被清 / 换设备 / 主动吊销

| 场景 | 行为 |
|---|---|
| Cookie 被清（浏览器清数据） | Fallback 到 **Passkey 一键恢复**（Face ID 一下），不动电脑，不扫码 |
| 手机丢了 | 桌面端「我的设备」列表 → 一键吊销 → 该设备 L2 立即作废、WebSocket 断连 |
| 换新手机 | 走一次完整配对（正常，属于「新设备加入」） |
| 疑似泄露 | 立即吊销该设备 + 吊销全部设备 + 轮换服务端签名密钥 |

## 2. 一个必须踩对的坑：长期凭据存哪里

这一条如果做错，「长期有效」就是假的。以下是 WebKit 官方 ITP 规则（已实测核对）：

| 存储方式 | 7 天无交互后 | 结论 |
|---|---|---|
| `document.cookie`（JS 写） | **被清空** | ❌ 不能用 |
| `localStorage` | **被清空** | ❌ 不能用 |
| `IndexedDB` | **被清空** | ❌ 不能用 |
| Service Worker 注册 | 被清空 | ❌ 不能用 |
| **服务端 `Set-Cookie`（httpOnly + Secure + SameSite）** | **不受 7 天限制** | ✅ **唯一正解** |

> WebKit 原文：ITP「deletes all cookies created in JavaScript and all other script-writeable storage after 7 days of no user interaction」，但「cookies created through `document.cookie` cannot be HttpOnly which means authentication cookies should not be affected by the lifetime cap. If they are, you need to set your authentication cookies in an HTTP response and mark them Secure and HttpOnly.」

**所以：L2 必须是服务端下发的 httpOnly Cookie，属性如下**

```
Set-Cookie: ut_device=<opaque-random-256bit>;
            HttpOnly; Secure; SameSite=Strict;
            Path=/; Max-Age=15552000        # 180 天
```

配套措施：
1. **滑动续期**：每次成功用 L2 换 L3 时，重发一次 Set-Cookie 刷新 Max-Age。
2. **7 天限制的本质是「7 天无交互」**：你日常用，计数器一直重置。即使真被清，降级也只是「重新配对一次」，不会丢数据。
3. **主动申请持久化存储**：调用 `navigator.storage.persist()`。注意 iOS 上这个 API 需要**通知权限**才会生效 —— 这是一个隐藏耦合，要在引导页里一起请求。
4. **不要依赖 Cookie 做唯一恢复手段**：Passkey 是二阶兜底（见下节）。

> ⚠️ 反面案例：很多自研项目把 refresh token 塞 localStorage，然后抱怨「iOS 上每周都要重新登录」。根因就在这里，不是逻辑 bug。

## 3. 便利性：Passkey 是「安全 + 便利」同时成立的那把钥匙

### 3.1 为什么是 Passkey

| 维度 | 长命 Cookie（L2） | 密码 | **Passkey (WebAuthn)** |
|---|---|---|---|
| 泄露风险 | 中（可被 XSS/中间人截获，但 httpOnly 挡了 XSS） | 高（可被钓鱼、撞库） | **极低（私钥不出设备安全芯片，不可导出、不可复制）** |
| 钓鱼抗性 | 无 | 无 | **有（凭据绑定 origin）** |
| 用户体验 | 无感 | 要记要输 | **Face ID 一下（<1s）** |
| 长期有效性 | 受存储回收影响 | 永久但可被盗 | **凭据在 Secure Enclave，长期稳定** |
| 服务端保管 | token 明文（等于密码） | 哈希 | **只有公钥，泄露也没用** |
| 吊销 | 删记录 | 改密码 | **删公钥** |

### 3.2 定位（重要）

**不是用 Passkey 替换 Cookie，而是让两者互补：**

- **Cookie（L2）= 无感通道**：日常打开零交互，直接进。
- **Passkey = 设备存在性证明 + 恢复通道 + 高危操作二次确认**：
  - Cookie 被清 → Passkey 一键恢复（不用回电脑）
  - 删除会话 / 吊销设备 / 修改配置 → 要求 Passkey 验身
  - 检测到异常（新 IP 段 / 新 UA）→ 要求 Passkey 重新验证

**为什么这个组合能同时满足三个目标**：Cookie 提供「便利」，Passkey 提供「安全」，两者叠加让「长期有效」有了一个不怕丢的锚点。

### 3.3 iOS 上的可行性（已核实）

- iOS 16+ 的 Safari **完全支持**在「已添加到主屏幕」的 PWA 里使用 WebAuthn，Face ID / Touch ID 可用。
- 私钥存 Secure Enclave；可选择经 iCloud Keychain 同步（便利，但也意味着会同步到你其他 Apple 设备 —— 自用场景可接受，介意就设 `authenticatorSelection.residentKey = 'required'` + 不依赖同步）。
- 实现直接用标准库，不要手搓密码学。

## 4. 回答「在什么基础上修改」

### 4.1 结论

> **不 fork 任何项目。在「Web 标准 + 3 个现成库 + 1 个现成隧道工具」之上，自研约 400~600 行胶水代码。**

### 4.2 为什么不能 fork 现成项目

| 候选 | 为什么不能 fork |
|---|---|
| **Happy**（23,744★） | 它是 Expo/React Native 单体 App + Postgres + Redis + MinIO + K8s 全套。你要的是**单进程 + SQLite + 纯浏览器**，架构目标正相反。**但它的加密设计文档（MIT）是极好的参考，可以「照着设计自己写」。** |
| **claudecodeui**（13,649★） | **AGPL-3.0，传染**。只要抄了代码，你的 MIT 就没了。只能看架构，不能抄实现。 |
| **herdr** | 它的核心价值（PTY 持久化 + 状态检测）在 ACP 路线下要么被协议取代，要么不是瓶颈。且 Windows 不能做 `--remote` 目标主机。**降级为远期可选后端。** |
| **acpx** | **不是 fork，是依赖**。MIT，直接用，它已经解决 22 个 Agent 的统一接入。 |

### 4.3 真正复用的「基础」（依赖清单，版本已实测）

### 4.4 自研范围（明确边界）

```
自研（~500 行）:
  ├── 配对码签发/校验/自焚        ~100 行
  ├── 设备表 CRUD + 吊销 + 踢线    ~120 行
  ├── L3 签发/校验/续期            ~100 行
  ├── Passkey 注册/验证（调库）    ~120 行
  └── 扫码页 + 设备管理页 UI       ~60 行

不自研（全部用现成的）:
  ├── Agent 接入          → acpx
  ├── 密码学              → WebCrypto / simplewebauthn / libsodium
  ├── 终端                → node-pty + xterm.js
  ├── 网络穿透            → Tailscale / cloudflared
  └── PWA 打包            → vite-plugin-pwa
```

**没有一个自研模块是「需要发明新东西」—— 全都有成熟标准可循。这是这个方案可控的根本原因。**

### 4.5 自研的纪律：三条红线（回答「全部自己写会不会有问题」）

**结论：可行，但必须接受一个约束 —— 你写的不是「聪明的代码」，而是「无聊的标准代码」。无聊是安全的朋友。**

**纪律 1：密码学零自研（绝对红线）**

| ❌ 禁止 | ✅ 允许 |
|---|---|
| 自己实现加密/签名/KDF 算法 | 调用 `node:crypto`、`libsodium`、`@simplewebauthn/*` |
| 「把 token 加个盐 base64 一下」这类自创混淆 | 用 HMAC-SHA256 / AES-GCM 等标准原语 |
| 用 `Math.random()` 生成任何凭据 | 只用 `crypto.randomBytes()` / `crypto.getRandomValues()` |
| 用 `===` 比较 token 或 MAC | 用 `crypto.timingSafeEqual()` |

> 判断标准：**如果你在代码里写了 `for` 循环去逐字节处理密钥材料，大概率已经错了。**

**纪律 2：流程照抄标准，不要自创**

- 设备授权流程 → 参考 OAuth 2.0 Device Authorization Grant (RFC 8628)
- 会话轮转 → 参考 OAuth 2.1 refresh token rotation（含重放检测）
- Passkey → 照抄 `@simplewebauthn` 官方示例，不要「简化」
- **不要为了「代码简洁」而砍掉安全流程的步骤** —— 每一步都有存在理由

**纪律 3：把安全清单写成自动化测试，不靠记忆（最关键）**

自研认证最常见的失败**不是算错，而是漏了**：

| 常见遗漏 | 后果 | 对应的自动化断言 |
|---|---|---|
| 忘记限流 | 配对码可爆破 | 连发 100 次配对请求 → 断言后续被拒 |
| 吊销时不断连 | 吊销了但会话还能用 | 吊销后断言 WebSocket 已断开 |
| Cookie 漏 `SameSite` | CSRF | 跨站请求 → 断言被拒 |
| Cookie 漏 `Secure`/`HttpOnly` | 降级攻击 / XSS | 断言响应头完整 |
| 配对码可重复消费 | 重放攻击 | 同一码用两次 → 断言第二次失败 |
| token 比较非恒定时间 | 时序侧信道 | 代码审查 + 断言用 `timingSafeEqual` |
| 密码学随机源用错 | 凭据可预测 | 断言 `crypto.randomBytes` 被调用 |
| 密钥/密文泄漏进日志 | 日志即后门 | 断言日志中不含 token 字段 |

**为什么「半年后还能看懂」是可行的**：因为全是标准流程、没有「聪明的技巧」。如果哪天你觉得某段认证代码「很巧妙」，那就是该重写它的信号。

**一个更保守的退路（不推荐，但你该知道）**：
- **Cloudflare Access** —— 零代码零信任认证。代价：绑定 CF，且属于网关认证而非应用内认证（细粒度权限做不了）。
- **Authelia / Authentik** —— 自托管 SSO。但为「多用户企业」设计，对单用户自用要额外跑 PostgreSQL + Redis，是巨大过度设计。

→ 因此仍推荐自研薄层，但**三条纪律必须守住**。

## 5. 安全加固清单（对标 ZCode 的设计债）

| # | ZCode 的问题 | 本方案的做法 |
|---|---|---|
| 1 | 链接即授权 | **配对码 5 分钟 + 单次 + 用完即焚**；L1 只能「请求」，不能「授权」 |
| 2 | 关闭弹窗不停止远控 | 无隐藏常驻状态；所有会话在服务端可见、可单独终止 |
| 3 | 无法吊销 | **设备表 + 一键吊销 + 立即踢线**（吊销时主动断 WebSocket，不等 token 过期） |
| 4 | 无有效期概念 | **L3 15 分钟 / L2 滑动 180 天 / L1 5 分钟**，三层各有寿命 |
| 5 | 单一凭据泄露即全失守 | 三层分离，L3 泄露换不到 L2 |
| 6 | 无审计 | 设备列表带 **最后活跃时间 / IP / UA / 位置估计**；登录、吊销、高危操作全部留痕 |
| 7 | 无异常检测 | 新 IP 段或新 UA → 降级为「需要 Passkey 重新验身」 |
| 8 | 无速率限制 | 配对接口按 IP 限速 + 全局未消费配对码上限（防爆破） |
| 9 | 传输层裸奔 | 默认走 **Tailscale（WireGuard E2E）**；如走 Cloudflare Tunnel 则**必须叠加应用层 E2E**，否则 CF 可见明文 |
| 10 | 权限边界模糊 | 权限请求（ACP `session/request_permission`）**在手机上必须显式点击**，无「静默批准」 |

**额外一条（ZCode 完全没有的）**：**「正在被谁控制」的可见性**。桌面端应始终能一眼看到「当前有 N 台设备在线 / 正在执行什么」，而不是一个不显眼的弹窗。

## 6. 传输层：先分场景，再做可插拔适配

### 6.0 先纠正一个前提：不需要 VPS

「不是所有人都能自建 VPS」—— 完全正确，而且**方案根本不需要 VPS**。

但物理约束也在：**「零安装 + 零配置 + 零费用 + 任何网络可达」四者不可兼得。** 必须存在某个「公网可达的端点」——要么你的机器自己就是（公网 IP / IPv6），要么有个中转。所以正确的做法不是找一个「全能方案」，而是**按场景分层，把每一层的代价压到最低**。

### 6.1 场景分层（频率差异巨大，这是设计的基础）

| 场景 | 频率 | 需要什么 | 方案 |
|---|---|---|---|
| **S1 在家（同 WiFi）** | **最高频**（预计 70%+） | **什么都不需要** | **局域网直连，零配置** |
| S2 在外（4G / 公司网） | 次高频 | 需要穿透 | 见 6.3，三选一 |
| S3 分享给他人 | 少见 | 公网 URL | Cloudflare Tunnel |

> **S1 是零配置的** —— 沙发上/床上用手机控制书房的电脑，局域网直连即可。**把默认做成零配置，让绝大多数使用场景不需要任何网络设置。这是「便捷性」的第一层答案。**

### 6.2 适配器清单（配置项切换，别写死）

```yaml
transport: lan | cloudflare | easytier | ipv6 | frp | manual
```

| 模式 | 手机要装 | 需要域名 | 需要 VPS | 国内延迟 | 隐私 | 定位 |
|---|---|---|---|---|---|---|
| `lan` | ❌ | ❌ | ❌ | <5ms | 完全 | **默认，零配置** |
| `cloudflare` | ❌ 纯浏览器 | ✅ ~¥30/年 | ❌ | 几十~上百 ms | ⚠️ CF 见明文 | **外网 · 零安装首选** |
| `easytier` | ✅ EasyTier | ✅ | ❌ | **20-60ms** | ✅ 端到端 | **外网 · 低延迟首选** |
| `ipv6` | ❌ | ✅ DDNS | ❌ | **最低** | ✅ 全自主 | 进阶 |
| `frp` | ❌ | ✅ | ✅ | 看 VPS | ✅ | 高级选项 |
| `manual` | — | — | — | — | — | **逃生舱** |

`manual` 很重要：允许用户直接填任意 URL（他自己用 ngrok / 公司 VPN / 别的什么都行），我们不限制。

### 6.3 ⚠️ 收回：Tailscale 不能作为默认（国内不成立）

第一轮曾推荐 Tailscale 作为默认传输层，**查证实测资料后收回**：

| 问题 | 实测情况 |
|---|---|
| **登录** | 走 Google / Microsoft / GitHub OAuth，**国内无梯子基本无法完成** |
| **中继** | 官方 DERP 全在境外，国内节点 P50 延迟约 **250ms** |
| **打洞** | 国内 P2P 打洞成功率 **仅 30~60%**，多数情况退化为走海外中继 |
| **结论** | **对国内用户基本不可用。** Headscale 自建能解决，但那需要 VPS —— 正好踩中要避开的坑。 |

### 6.4 三个可行的外网方案

**方案甲：Cloudflare Tunnel —— 零安装首选**

- ✅ 免费、免备案、**无需公网 IP、无需 VPS、零运维**
- ✅ 手机纯浏览器 → 完美满足「扫码即用不装 App」
- ✅ 自动 HTTPS、自带 DDoS 防护
- ⚠️ 需要**一个域名**（约 ¥30/年）并把 NS 托管到 CF。这是最低门槛，但确实是门槛。
- ⚠️ 国内走境外节点（香港/新加坡/美国），延迟几十~上百 ms，晚高峰有跨境拥堵
- ⚠️ **CF 在边缘解密流量**（这是它 WAF / 缓存能力的前提）→ 代码、对话、diff 对 CF 是明文 → **必须叠加应用层 E2E**（正好与 6.5 的密钥交换预留对上）
- 📌 对「事件流 + diff + 日志」这类小体量文本，速度绰绰有余（已核实的结论）

**方案乙：EasyTier + Cloudflare Workers 中继 —— 低延迟 / 高隐私首选**

- EasyTier 是**国产去中心化组网**（Rust，LGPL-3.0）
  - 双对称 NAT 直连率 **60%+**（Tailscale <5%）
  - 国内延迟 **20-60ms**
  - 无需注册账号、去中心化、带 Web 管理界面（可看完整路由路径）
  - 支持 Win / macOS / Linux / **Android** / OpenWrt
- ⚠️ 官方公共中继**已停止维护**，需要自建对等节点
- ✅ **用 Cloudflare Workers 做对等节点是免费的**（现成项目 `easytier-ws-relay`），仍然不需要 VPS
- ⚠️ 注意：CF 的 `workers.dev` 子域在大陆**无法访问**，所以还是需要一个自己的域名
- 📌 代价：手机要装 EasyTier 客户端。但它是**通用组网工具**，装一次还能连家里 NAS 等别的设备 —— 性质与「必须装 Happy」完全不同。

**方案丙：IPv6 直连 —— 延迟最低、最自主**

- 国内三大运营商家宽普遍提供 IPv6；手机 4G/5G 也基本有 IPv6
- 双方都有 IPv6 → **直连，零第三方、零成本、延迟最低**
- ⚠️ 需要：路由器放行 IPv6 入站、DDNS（地址会变）、目标网络支持 IPv6（很多公司 WiFi 只有 IPv4）
- 📌 适合作为进阶选项，不能作为默认

### 6.4.1 「通用性」的最终结论

> 最低门槛 = **一个域名（约 ¥30/年）**。不需要 VPS、不需要备案、不需要公网 IP。
>
> 有了域名：要「零安装」（手机纯浏览器）→ Cloudflare Tunnel；要「低延迟 + 高隐私」→ EasyTier + CF Workers 中继。
>
> **这比自建 VPS（几百元/年 + 运维）低一个数量级。**

产品上不要替用户选，而是**向导 + 自动检测**：首次启动时自动探测（有没有公网 IPv6？装了 EasyTier 吗？配了域名吗？），直接给结论「当前可用：局域网（已就绪）；要外网访问，推荐 X」，并提供一键配置。

### 6.5 一个必须在 MVP 就定下来的架构决定

> **配对流程里是否携带密钥交换？**

即使 v1 不做 E2E 加密，**配对时的密钥交换步骤也要预留**。因为：如果 v1 的配对流程只是「发一个 token」，那么将来要加 E2E 时，**所有已配对设备都必须重新配对一次**（因为它们的密钥不是配对时交换的）。

参考设计（Happy 的做法，MIT 文档公开，可照着写）：
- 手机生成 X25519 密钥对，私钥留在设备，公钥发给服务端
- 桌面端批准时，把「账户密钥」用手机公钥加密后交给服务端
- 手机用私钥解密 → 服务端**全程看不到账户密钥**
- 日常数据用账户密钥派生的子密钥做 AES-256-GCM 加密，服务端只存密文

**建议**：v1 就把「手机生成密钥对 + 服务端转交加密载荷」这一步做进去（成本极小，约 30 行），但先不做数据加密。这样 v2 上 E2E 时**不需要重新配对**。

### 7.2 四条设计原则（针对手机）

1. **终端默认收起，按需展开。**
   它是兜底视图，不是主视图。只有 PTY 兜底通道（无 ACP 的 TUI 工具）才强制展示终端。

2. **状态优先于内容。**
   手机屏幕小、注意力短。首屏应该回答三个问题：**它在干什么？卡在哪？要我做什么？** —— 而不是「它输出了 300 行日志」。

3. **权限请求必须做成原生感的底部操作单。**
   这是手机上最高频、最关键的交互。一个「允许/拒绝」按钮太小、太容易点错。用 bottom sheet + 大按钮 + 显示「要执行什么命令」。

4. **断线重连 + 事件重放是硬需求，不是优化项。**
   手机切后台、切网络、锁屏是常态。WebSocket 必须支持带 `lastEventId` 重连，服务端补齐断档事件。**没有这个，手机上就是「一半时间在转圈」。**

## 8. PWA vs 原生 App：边界在哪、能不能套壳

### 8.1 能力边界（iOS 为重点）

| 维度 | PWA（添加至主屏幕） | 原生 App |
|---|---|---|
| 分发 | 扫码开 URL → 添加到主屏幕 | App Store / TestFlight / 侧载 |
| 安装 | 无（或一键添加） | 下载安装 |
| 更新 | **自动**（Service Worker） | 需重新下载 |
| 推送 | ✅ iOS 16.4+，但**必须已添加到主屏幕** | ✅ 完整 |
| **后台运行 / 后台同步** | ❌ **无** | ✅ 有 |
| 本地能力 | 相机/麦克风/文件 ✅；蓝牙/后台定位/通讯录 ❌ | 完整 |
| 存储稳定性 | 可能被回收（需申请 `persist()`） | 稳定 |
| 上架成本 | **零** | $99/年 + 审核 + 合规 |
| 跨平台 | 一套代码 | 每平台一套 |

### 8.2 关键判断：PWA 最大的短板在本场景不成立

> **后台运行 / 后台同步 —— 我们不需要。**
>
> 因为**任务跑在你的电脑上，不在手机上**。手机只是个遥控器：发指令、看事件、点批准。它不需要在后台执行任何计算，也不需要后台同步。

一旦把这个短板排除，PWA 对本场景的适配度就**非常高**：跨平台一套代码、零上架成本、扫码即用、自动更新、还能加到主屏幕 + 推送。

### 8.3 能不能「用壳装 PWA」？能，有三条路

| 方式 | 原理 | 平台 | 改动量 | 备注 |
|---|---|---|---|---|
| **TWA**（Trusted Web Activity） | Chrome 内核直接渲染 PWA，发布到 Google Play | 仅 Android | **几乎为零** | Google 官方支持的标准做法 |
| **Capacitor** | 把 PWA 打进原生壳（Android WebView / iOS WKWebView） | Android + iOS | 低，业务代码基本不改 | 可逐步加原生插件（推送/生物识别/文件） |
| **Tauri Mobile** | Rust 壳 + 系统 WebView | Android + iOS | 中 | 与 Tauri 桌面端可共用 |
| ❌ 纯网页包壳上 iOS | — | — | — | **Apple Guideline 4.2.2 明确拒绝 "repackaged websites" / "web clippings"，会被拒审** |

⚠️ **iOS 上架有个硬坑**：直接把网页包个壳提交会被 Apple 拒。要过审必须加入**真正的原生能力**（原生通知增强、原生分享、离线缓存、快捷指令等），让它不只是「一个网页」。

### 8.4 建议：一期只做 PWA

- **一期**：只做 PWA。这本身就是差异化 —— **「扫码即用，不装 App」**（Happy 必须装专用 App）。
- **二期**：如果确实需要 App 的**分发渠道或信任感**，用 Capacitor 接壳。因为 PWA 与 Capacitor 共享同一套 Web 代码，**接壳几乎零成本**（不改业务代码，只加插件）。
- **套壳的真实价值不是功能**（功能 PWA 都有），**而是「有个 App 看起来更靠谱」的心理预期 + 应用商店的曝光**。对自用 + 开源阶段，这两点都不急。

### 8.5 ⚠️ 但必须承认 PWA 的一个真实成本

iOS 上「添加到主屏幕」是**用户手动完成**的，Safari 的入口藏得深（分享按钮 → 下滑 → 添加到主屏幕），而且**没有 `beforeinstallprompt` 可以主动触发**。而推送和 standalone 模式都依赖这一步。

→ **所以第一屏必须做图文引导**，这不是「优化项」，是「能不能用起来」的关键节点。

## 10. MVP 验证清单（单 Agent 闭环）

**目标：验证两个真正的技术风险点，而不是验证 acpx 能不能跑（它当然能跑）。**

```
┌──────────┐  ①扫码(一次性)   ┌──────────┐  ②WebSocket  ┌──────┐  ③ACP   ┌─────────────┐
│ 手机 PWA  │ ───────────────► │ Node 服务 │ ───────────► │ acpx │ ──────► │ Claude Code │
│          │ ◄─────────────── │          │ ◄─────────── │      │ ◄────── │             │
└──────────┘  ④事件流+面板      └──────────┘  结构化事件   └──────┘   stdio  └─────────────┘
```

### 两个真风险

| 风险 | 为什么是风险 | 验证方式 |
|---|---|---|
| **A. 配对 → 长期凭据链路** | 跨浏览器、跨 iOS ITP、跨 Cookie 语义，全是「只有实测才知道」的坑 | 关浏览器重开仍登录；清 Cookie 后 Passkey 恢复；服务端吊销后立刻踢线 |
| **B. 事件流跨网络到手机** | 手机网络抖动 + 切后台 + 重连重放，比本地回调复杂一个量级 | 切后台 30s 回来事件不丢；断网重连自动补齐 |

### 验证清单

```
认证链路
[ ] 扫码 → 配对 → 自动进入控制台
[ ] 关掉浏览器 / 重开 PWA → 仍处于登录态（L2 Cookie 生效）
[ ] 手动清 Cookie → 用 Passkey 恢复（不扫码、不碰电脑）
[ ] 服务端吊销设备 → 手机 WebSocket 立即断开并回到登录页
[ ] 伪造 / 重复使用配对码 → 被拒绝

Agent 链路
[ ] acpx 驱动 Claude Code 跑一个 prompt
[ ] agent_message_chunk 流式到达手机并正确渲染
[ ] tool_call 卡片出现、状态从 pending → completed
[ ] Claude Code 请求权限时，手机弹出底部操作单
[ ] 手机点「允许」→ Agent 继续执行

网络鲁棒性
[ ] 切后台 30 秒回来 → 事件不丢（重连 + 重放）
[ ] 切换 WiFi/4G → 自动重连
[ ] 服务端重启 → 手机自动恢复会话
```

### 明确不在 MVP 范围

- ❌ 多 Agent（acpx 支持 22 个，但先只跑通 1 个）
- ❌ PTY 兜底通道（node-pty + xterm.js）
- ❌ 外网穿透（先用局域网；`lan` 模式覆盖最高频场景且零配置）
- ❌ E2E 数据加密（但**配对时的密钥交换步骤要做进去**，避免将来重新配对）
- ❌ 多用户 / 权限隔离（自用，只有「你」一个身份）

## 11. 待讨论的决策点

| # | 决策 | 我的推荐 | 理由 |
|---|---|---|---|
| **D1** | E2E 加密：MVP 做还是后做？ | **MVP 不做，但把配对时的密钥交换预留好** | 走 Tailscale 时 WireGuard 已是 E2E，重复加密无收益。但配对流程若不预留密钥交换，将来加 E2E 要全员重新配对。 |
| **D2** | Cookie 和 Passkey，谁为主？ | **Cookie 为主（无感），Passkey 为辅（恢复 + 高危二次验证）** | 纯 Passkey 每次打开都要 Face ID，日常用起来烦；纯 Cookie 又没有不怕丢的锚点。 |
| **D3** | 默认传输走哪条？ | **默认 `lan`（零配置）；外网首选 `cloudflare`；追求延迟/隐私则 `easytier`** | ✅ Tailscale 国内不可用（已收回）。局域网覆盖最高频场景且零配置；两个外网方案都不需要 VPS，最低门槛只是一个域名。 |
| **D4** | L2 寿命设多长？ | **180 天滑动续期** | 足够「长期」，又不会「永久」。反正可吊销，长一点没关系。 |
| **D5** | 配对交互：谁扫码？谁批准？ | **手机扫码 + 桌面端点「允许」** | 台式机通常没摄像头（所以手机扫）；但**授权必须在可信设备上人工完成**（所以桌面批准）。二维码只是 pairId，不是凭据 —— 这是与 ZCode 的本质区别。 |
| **D6** | 手机端要不要做原生壳？ | **一期只做 PWA；壳作为二期可选的发布通道** | PWA 最大短板（无后台运行）在本场景**不成立** —— 任务跑在电脑上，手机只是遥控器。壳用 Capacitor 可几乎零成本接上；Android 也可走 TWA（免费上架）。 |
| **D7** | 认证自己写还是用现成方案？ | **自研薄层（~500 行），守三条纪律** | ① 密码学零自研 ② 流程照抄标准 ③ 安全清单写成自动化测试。用 Cloudflare Access 会绑定 CF；用 Authelia/Authentik 对单用户是巨大过度设计。 |
| **D8** | 外网访问的意愿成本？ | **待你确认** | 是否需要「出门在外」可用？能否接受买一个域名（约 ¥30/年）？这决定 S2 走哪条路。 |

## 附录 B：本方案的「长期可维护性」

「脱坑」的另一层含义是：项目要能长期放着不用管。支撑这一点的设计：

1. **薄的自己 + 厚的别人**：自研 500 行，其余全依赖成熟标准库。别人的库在维护，你的不用动。
2. **ACP 是协议不是适配器**：新增 Agent 零成本（永远走 `acpx <agent>` 的统一命令面），不像竞品每个 CLI 都要写适配器、跟着上游更新改。
3. **标准而非发明**：认证走 WebAuthn（W3C）、Cookie 走 RFC 6265、OAuth 式轮转。没有「我们自己的加密算法」这种会腐烂的东西。
4. **接口边界清晰**：Transport 层可插拔（局域网/Tailscale/CF），Agent 层可插拔（ACP/PTY）。任一层过时了换掉即可，不牵动全局。
5. **单进程 + SQLite**：没有 K8s、没有 Redis、没有对象存储。`git clone` + `npm i` + `npm start` 就能跑起来。三年后回来看还是这样。
