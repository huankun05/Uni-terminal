# 设计文档 02 · 一键安装、配对码加固、常驻服务与传输层定案

> 项目：Uni-terminal（统一 AI Coding Agent 终端控制台）
> 定位：自用 + 开源（MIT）
> 本文回答四个问题：① 能不能一键添加到桌面 ② 配对码怎么限流 + 怎么"随时间可变" ③ 电脑端常驻服务 + 凭证重连怎么做 ④ 传输层最终选什么

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| **一键添加到桌面** | **能做，但只有 Android/桌面 Chromium 能真·一键**。iOS Safari 只能引导，**微信内浏览器完全不行** —— 而国内扫码默认走微信，这是第一道坎。方案：三层降级。 |
| **配对码限流 + 时间可变** | 照 RFC 8628 做：**两个码分离**（设备码哈希存储 + 用户码短熵）+ **三层限流**（轮询侧 / 验证侧 / 全局）。**TOTP 不适用**，正解是**二维码短周期自动轮换**。 |
| **常驻服务 + 凭证重连** | 需要对标的是 RustDesk 的 `hbbs`（会合）+ `hbbr`（中继）模型，**但我们要轻得多** —— 方向固定（手机→电脑），不需要 ID 号码、不需要打洞。**Windows 上用「任务计划程序」而不是「Windows 服务」**，原因见 3.3。 |
| **传输层** | **分层默认**：在家走 `lan`（零配置）→ 在外走 `cloudflare`（零安装，只需一个域名）→ 进阶 `easytier`。**新增发现：`trycloudflare.com` 快速隧道可做零门槛试玩通道。** |

## 1. 「一键添加到桌面」——能做到什么程度，怎么兜底

### 1.1 三层现实（必须先接受这个分层）

| 平台 | 能力 | 做法 |
|---|---|---|
| **Android Chrome / Edge / 三星浏览器** | ✅ **真·一键** | 捕获 `beforeinstallprompt` → 自己画按钮 → 点击 `prompt()` |
| **桌面 Windows Chrome / Edge** | ✅ **真·一键** | 同上，装完出现在开始菜单 |
| **iOS / iPadOS Safari** | ❌ **不可能一键** | 只能图文引导「分享 → 添加到主屏幕」 |
| **微信 / QQ / UC 内置浏览器** | ❌❌ **完全不行** | 必须拦截 + 引导跳出到系统浏览器 |
| Firefox | ❌ 不支持 manifest 安装 | 提示换浏览器 |

**关键认知：安装动作必须由「用户手势」触发。** 这是浏览器的安全约束 —— 代码不能自动弹安装框，**键盘快捷键也不行**（快捷键不构成合规的用户手势）。

所以"快捷键"这个思路要放弃，换成：**在页面里放一个显眼的「装到桌面」按钮**。在支持的平台上，点它就是真·一键。

### 1.2 Chromium 上怎么做成"一键"

```js
// 捕获浏览器准备好的安装事件，先拦下来，等我们自己的按钮触发
let deferredPrompt = null;

window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();        // 不让浏览器自己弹小横条
  deferredPrompt = e;        // 存起来，等用户点我们的按钮
  showInstallButton();       // 只有这时才显示"装到桌面"按钮
});

installBtn.addEventListener('click', async () => {
  if (!deferredPrompt) return;
  deferredPrompt.prompt();                       // 弹原生安装框
  const { outcome } = await deferredPrompt.userChoice;  // 'accepted' | 'dismissed'
  deferredPrompt = null;                         // ⚠️ 只能调一次，用完即作废
  track('pwa_install', outcome);
});
```

**三个必须知道的约束**：

| 约束 | 说明 | 应对 |
|---|---|---|
| `prompt()` **只能调一次** | 用户拒绝后这个事件对象就废了 | 拒绝后降级为图文引导 |
| 拒绝后有**冷却期**（据实测约 3 个月） | 期间 `beforeinstallprompt` 不再触发 | **别乱弹** —— 只在配对成功后、用户最有动机的那一刻弹 |
| 已安装后不再触发 | 用于判断"是否已装" | 配合 `display-mode` 检测做双保险 |

**增值细节**：在 manifest 里补上 `description` + `screenshots`，Android Chrome 的安装弹窗会从一条小横条**升级成 App Store 风格的大弹窗**（带截图、评分位）。这对转化率的提升是实打实的，成本只是两张截图。

**新标准（可选）**：Chrome / Edge 143+ 正在 origin trial 阶段测试 Web Install API：
```js
await navigator.install();   // 更干净的一键安装，不需要先拦事件
```
→ **可以埋进去做渐进增强，但不能作为唯一路径**（还在试验阶段）。

### 1.3 iOS Safari：只能引导，但要做得"像一键"

iOS 上没有 `beforeinstallprompt`，唯一路径是用户手动操作。**我们的价值在于把这条路指引清楚。**

**检测 + 引导的实现**：

```js
// 是否已经运行在"已安装"的独立窗口里
const isStandalone =
  window.navigator.standalone === true ||                       // iOS 特有
  window.matchMedia('(display-mode: standalone)').matches;      // 标准

// 是否 iOS
const isIOS = /iPad|iPhone|iPod/.test(navigator.userAgent) ||
              (navigator.platform === 'MacIntel' && navigator.maxTouchPoints > 1);

if (isIOS && !isStandalone) {
  showIOSInstallGuide();   // 全屏引导浮层
}
```

**引导浮层的设计要点**（这是转化率的命门，不是装饰）：

1. **必须在配对成功之后弹，不能在首次打开就弹。** 用户还不知道这东西有什么用，凭什么装到桌面。
2. **做成动画指引，不要静态图。** iOS 的分享按钮在地址栏里，位置随版本变（iOS 15/16/17/18 都有差异），静态截图容易过期。用一个**从底部升起的小箭头指向分享按钮**的动画。
3. **给出"为什么值得装"的两个具体理由**：① 装完才有推送通知 ② 装完扫码一次就再也不用管（会话保持更稳）。
4. **提供一个「我装好了」按钮**，点完重新检测 `display-mode`；如果还是 false，说明没装成功，再教一次 —— **别让用户卡在死循环里**。

```
┌─────────────────────────────────┐
│                                 │
│     把它装到桌面，体验更好       │
│                                 │
│   ✓ 断线时能收到推送通知         │
│   ✓ 下次打开免扫码、直达会话      │
│                                 │
│        [ 图示动画演示 ]          │
│     ① 点底部中间的 ⬆ 分享        │
│     ② 下滑找到「添加到主屏幕」    │
│     ③ 点右上角「添加」           │
│                                 │
│   ┌───────────────────────────┐ │
│   │      我已添加好了          │ │
│   └───────────────────────────┘ │
│      以后再说（本次不再提示）      │
└─────────────────────────────────┘
```

### 1.4 ⚠️ 最大的坑：微信扫码 —— 国内场景的第一道坎

**这是本文最重要的发现，比 iOS 引导更关键。**

国内用户的默认行为是**用微信扫二维码**。但微信内置浏览器（Android 走 X5 内核 / iOS 走 WKWebView）的能力是残缺的：

| 能力 | 微信内 | 后果 |
|---|---|---|
| 添加到主屏幕 | ❌ **完全不支持** | 装不了 PWA |
| Service Worker | ❌ 不支持 / 部分失效 | **PWA 整个不成立** |
| **WebAuthn / Passkey** | ❌ **不支持** | **手机端 Passkey 恢复通道直接废掉** |
| Push API | ❌ 不支持 | 收不到通知 |
| IndexedDB / localStorage 容量 | ⚠️ 受限、可能被清 | 本地状态不稳 |
| Cookie 持久性 | ⚠️ 表现与系统浏览器不同 | 「长期有效」可能失效 |

**结论：微信内打开 = 整个方案残废。** 不是体验降级，是功能不可用。

**所以必须做硬拦截：**

```js
const isWeChat = /MicroMessenger/i.test(navigator.userAgent);
const isQQ = /\sQQ/i.test(navigator.userAgent) || /QQBrowser/i.test(navigator.userAgent);
const isInApp = isWeChat || isQQ;

if (isInApp) {
  renderFullScreenBlock();   // 全屏遮罩，不给"继续"按钮
}
```

**遮罩要做什么：**

1. **全屏遮罩，不放行** —— 因为放行了它也是个废页面，用户会以为是我们的 bug。
2. **给出分平台的具体步骤**（用户找不到那个入口）：
   - iOS 微信：右上角 `···` → 「在 Safari 中打开」
   - Android 微信：右上角 `···` → 「在浏览器打开」
3. **配一个「复制链接」按钮** —— 用户可以复制到浏览器里粘贴。这是最可靠的兜底。
4. **用箭头动画指向右上角的 `···`**，因为很多人根本不知道那里有菜单。

```
┌─────────────────────────────────┐
│           ╭─────────╮           │
│           │  ↗ 指示  │           │  ← 动画箭头指向右上角
│           ╰─────────╯           │
│                                 │
│    请在浏览器中打开              │
│                                 │
│  微信内置浏览器不支持桌面安装     │
│  和指纹验证，需要用系统浏览器。   │
│                                 │
│   ① 点右上角的 ···               │
│   ② 选择「在浏览器中打开」        │
│                                 │
│   ┌───────────────────────────┐ │
│   │      复制链接               │ │
│   └───────────────────────────┘ │
└─────────────────────────────────┘
```

**另一个改进**：二维码本身旁边就写一句 **「请用相机 / 系统浏览器扫码，不要用微信扫」**。把问题挡在扫码之前，比拦在扫描之后好。微信扫一扫能识别普通 URL 二维码，用户用相机扫也会自动跳到系统浏览器。

### 1.5 实现清单

```
安装引导模块
[ ] Chromium: 捕获 beforeinstallprompt → 自定义按钮 → prompt()
[ ] Chromium: userChoice 埋点（接受/拒绝），拒绝后不再骚扰
[ ] manifest: 补齐 description + screenshots（换取 App Store 风格弹窗）
[ ] manifest: display=standalone, 完整 icons(192/512/maskable), start_url, id
[ ] iOS: 检测非 standalone → 配对成功后弹动画引导
[ ] iOS: 「我装好了」按钮 → 重新检测 → 失败可重试
[ ] 微信/QQ: UA 检测 → 全屏遮罩 + 分平台步骤 + 复制链接
[ ] 全局: display-mode 检测 → 已安装则永不显示任何安装引导
[ ] 渐进增强: navigator.install() 存在时优先用它
```

## 2. 配对码加固：业界标准做法

### 2.1 先纠正一处设计：两个码必须分开

**这是 RFC 8628（OAuth 2.0 Device Authorization Grant）的核心设计，我上一版文档把两者混成一个 `pairId` 了，需要拆开。**

| | **设备码 `device_code`** | **用户码 `user_code`** |
|---|---|---|
| 给谁用 | 机器（程序轮询） | 人类（看一眼 / 输入） |
| 长度 | 40 字符 base-62（~238 bit） | 8 字符 |
| 字符集 | 全字符 | **`BCDFGHJKLMNPQRSTVWXZ`**（base-20，去元音去歧义） |
| 熵 | ~238 bit | 20⁸ ≈ **2.56 × 10¹⁰** |
| 存储 | **SHA-256 哈希后存**（永不存明文） | 明文（要给人看） |
| 可见性 | **绝不显示给用户** | 显示 / 编进二维码 |

**为什么字符集要去掉元音和歧义字符**：RFC 8628 明确规定 —— 去掉 `AEIOU` 是为了避免随机拼出单词；去掉 `0/O`、`1/l/I` 是为了避免读错输错。这不是洁癖，是可用性要求。

**为什么用户码只有 8 位就够**：熵 2.56×10¹⁰ 本身不算大，但配上「5 分钟寿命 + 3 次失败即作废」后，爆破在数学上不可行：

```
可用尝试次数 = 3 次 / 码
一个码的生命周期内，随机猜中的概率 ≈ 3 / 2.56e10 ≈ 1.2e-10
攻击者要成功需要约 8.5e9 次完整配对会话 —— 且每次都需要目标用户不察觉地拿到新码
```

**关键：必须把"码"和"手机公钥登记"绑定**。也就是 RFC 8628 里的「设备绑定」思想（业界实现常叫 `device_binding_hash`）：

> 签发码时记下**发起方的指纹**（UA + IP 段 + 一个客户端生成的随机 nonce），手机来领 token 时校验指纹一致。
> 否则：攻击者偷看到二维码 → 抢先登记自己的公钥 → 用户的桌面端点了「允许」→ 攻击者拿到凭据。

这个绑定是**必需的，不是可选的**。

### 2.2 限流：三层，缺一不可

**只做一层限流是这个设计最常见的失败方式。** 三层要分别防不同的东西：

| 层 | 防什么 | 做法 |
|---|---|---|
| **① 轮询侧**（发码方） | 高频轮询打爆服务端 | 最小间隔 `interval=5s`；违反 → 返回 `slow_down` 错误，并把该会话的 interval **+5s**（RFC 8628 明确规定） |
| **② 验证侧**（输码/批码方） | 枚举爆破用户码 | 按 **IP + 全局** 双维度限流；**失败计数：失败 3 次 → 直接作废该码**（不是只拒绝请求） |
| **③ 全局** | 攻击者批量申请占满资源 | 未消费码总数上限（如 100）；每 IP 同时未消费码上限（如 3）；签发速率上限 |

**第 ② 层里"作废而不是拒绝"是关键**。如果只是拒绝请求，攻击者可以对着一个码慢慢试（每次间隔久一点绕过限流）；直接作废的话，他一试目标用户就得重新生成，攻击成本立刻爆炸。

**还要有一个"整体熔断"**：如果某个 IP 在窗口内触发了 N 次「码作废」，直接封禁该 IP 一段时间。

### 2.3 「根据时间可变」——TOTP 不适用，正解是短周期轮换

先说结论：**这里不该用 TOTP**。

**为什么 TOTP 不适用**：

| TOTP 的前提 | 我们的情况 |
|---|---|
| 双方**预先共享一个密钥** | ❌ 手机此刻还没配对，**没有共享密钥** |
| 用于**持续性的身份验证** | ❌ 配对是**一次性交互** |
| 时钟同步要求 | 手机和电脑时钟可能有偏差 |

强行套 TOTP 会变成"用时间做盐的一次性码"，**安全性不比随机码高，但复杂度和出错概率高得多**。这是典型的"为了巧妙而巧妙"，属于我文档 01 里定的纪律 2 要避免的东西。

**用户要的"随时间可变"，正解是：二维码短周期自动轮换。**

```
二维码里的 pairId 每 30~60 秒自动换一个
  ├─ 前端定时器到点 → 请求新的 pairId → 重绘二维码
  ├─ 旧 pairId 立即作废（从内存表删除）
  └─ 整个配对窗口仍有 5 分钟总寿命（防止无限轮换拖时间）
```

**这个效果比 TOTP 更好**：
- 截图偷拍基本无效（30 秒后那个码就死了）
- 不需要共享密钥、不需要时钟同步
- 用户看到二维码在闪动，**直观地理解"这东西是临时的"**（这本身是个好的安全提示）

**加一个体验细节**：二维码上叠一个**倒计时环形进度条**，用户能看见"还有 20 秒过期"。这比突然失效后莫名其妙要友好得多。

**更好的做法（可选）**：干脆**二维码只给一次**。第一次扫描就消费掉，如果手机中途断了（比如误退出浏览器），用户点一下"重新生成"即可 —— 简单、安全、行为可预测。

### 2.4 落地参数表

| 参数 | 值 | 来源 / 理由 |
|---|---|---|
| 用户码字符集 | `BCDFGHJKLMNPQRSTVWXZ` | RFC 8628 §6.1 |
| 用户码长度 | 8（显示为 `XXXX-XXXX`） | RFC 8628 示例 |
| 设备码 | 40 字符 base-62，**SHA-256 存储** | RFC 8628 及各实现共识 |
| 配对总寿命 | **5 分钟**（`expires_in=300`） | 我们场景下扫码是即时的，5 分钟足够；比 RFC 默认的 15~30 分钟更紧，更安全 |
| 二维码轮换周期 | **30 秒** | 短于任何人工偷拍的利用窗口 |
| 轮询最小间隔 | **5 秒** | RFC 8628 默认 |
| `slow_down` 惩罚 | interval **+5s** | RFC 8628 §3.5 |
| 验证失败阈值 | **3 次 → 作废该码** | 抗爆破的关键 |
| 未消费码总量上限 | 100（全局）/ 3（每 IP） | 防资源占满 |
| 设备绑定 | UA + IP 段 + 客户端 nonce 哈希 | 防"偷看二维码抢先登记" |
| 单次消费 | **严格一次性**，用后即焚 | 防重放 |

### 2.5 必须写进自动化测试的断言

对应文档 01 的「纪律 3」：

```
[ ] 同一 user_code 被消费两次 → 第二次必须失败
[ ] 同一 user_code 连续输错 3 次 → 该码立即作废，第 4 次即使输对也失败
[ ] 轮询间隔 < 5s → 返回 slow_down，且下次 interval 变大
[ ] 用 A 设备的指纹签发，B 设备来领 → 必须失败（设备绑定生效）
[ ] 二维码轮换后，旧 pairId → 必须失败
[ ] 配对窗口超过 5 分钟 → 必须失败
[ ] 连发 100 次 /pair/new → 断言后续被限流拒绝
[ ] 响应头中不含 pairId / device_code 明文
[ ] 日志中不含 device_code / 凭据字段
[ ] 用户码的随机源是 CSPRNG（不是 Math.random）
```

## 3. 常驻服务 + 凭证重连（参考远程软件的架构）

### 3.1 先看 RustDesk 的模型

RustDesk 用两个服务端组件（这是远程软件的经典架构，TeamViewer / 向日葵 / AnyDesk 内核思路一致）：

| 组件 | 职责 | 流量特征 |
|---|---|---|
| **`hbbs`**（ID / 会合 / 信令服务器） | 设备注册 ID + **持续心跳上报自己的 IP:port**；连接时协调双方**打洞** | 极小、恒定，几乎不花钱 |
| **`hbbr`**（中继服务器） | 打洞失败时转发数据 | **就是会话本身**，花钱的是它 |

核心机制：
1. 设备一上线就**持续 ping 会合服务器**，让它知道"我在这个 IP:port"
2. 要连接时，A 问会合服务器"B 在哪" → 会合服务器尝试让 A、B **直接打洞**
3. **打洞成功 → 中继完全不参与**（大多数情况）；失败 → 退化走中继
4. **会话端到端加密**（Curve25519 + xSalsa20-Poly1305），**中继只见密文**

**一个重要的安全机制值得抄**：RustDesk 服务端首启生成 **Ed25519 密钥对**，公钥配置进所有客户端。客户端连服务器时验签 —— 这样即使 DNS 被劫持、服务器被冒充，客户端也能识破。**这是我们要抄的。**

### 3.2 我们的模型不一样，不需要那么重

**关键差异：我们的连接方向是固定的（手机 → 你的电脑），不是任意两台设备互连。**

| RustDesk 需要 | 我们需要吗 | 原因 |
|---|---|---|
| ID 号码系统 | ❌ **不需要** | 你只有自己的电脑，没有"连未知设备"的需求 |
| 打洞（NAT 穿透） | ❌ **不需要** | 我们是**被动监听**，手机主动连 —— 门是开着的，不需要在墙上打洞 |
| 中继服务器 | ✅ **外网模式需要** | 但不是为了打洞，是**为了给内网服务一个公网入口**（本质是反向隧道，和 frp 同类） |
| 会合服务器（地址注册） | ✅ **需要，但可以很轻** | 因为你的外网地址会变（家宽 IP 变、隧道域名变） |

**所以我们的模型是三件事：**

```
① 常驻 Agent（电脑端）
     开机自启 · 维持设备表 · 监听连接 · 驱动 acpx

② 地址发现（手机怎么找到它）
     局域网：广播/mDNS 或固定 IP
     外网：固定的隧道域名（地址由隧道提供，天然稳定）

③ 凭证重连（手机凭什么都连上）
     L2 Cookie（httpOnly，长期）→ 换 L3（15 分钟）→ 建 WebSocket
```

**好消息：因为用了固定域名的隧道，"地址发现"在外网模式下自动解决了** —— 不需要会合服务器。这比 RustDesk 又轻一层。

### 3.3 电脑端常驻：任务计划程序 vs Windows 服务（重要判断）

**结论：用「任务计划程序」，不用「Windows 服务」。**

| 方式 | 能不能跑 | 推荐度 | 理由 |
|---|---|---|---|
| **任务计划程序**（登录时启动） | ✅ | ⭐⭐⭐ **推荐** | 以**你的用户身份**运行 —— 能读到你的配置、继承你的 PATH、能调 `claude` / `codex` CLI、能写你的项目文件 |
| 任务计划程序（开机启动，不登录） | ⚠️ | ⭐ | 同样能跑，但交互式 Agent（需要写用户目录）可能出问题 |
| NSSM / WinSW 包装成 Windows 服务 | ✅ 技术上可行 | ⭐⭐ 备选 | 真服务、开机即启、自动重启。**但跑在 Session 0** —— 见下面的坑 |
| `node-windows` / `qckwinsvc` | ✅ | ⭐ | 本质是 NSSM 的 Node 封装，省点事 |
| PM2 + `pm2-windows-service` | ⚠️ | ❌ 不推荐 | PM2 主要为 Linux 设计，Windows 下常出问题 |

**为什么服务模式有坑（这是决定性的）**：

Windows 服务跑在 **Session 0**，与用户桌面会话隔离。后果：

1. **拿不到用户的 PATH** → 找不到 `claude`、`codex`、`node` 这些安装在用户目录下的 CLI
2. **拿不到用户的凭据 / 环境变量** → Agent 的 API Key、git 凭据全部失效
3. **任何 GUI 交互会失败或弹到不可见的地方**

> 📌 这条我们**已经有前车之鉴**：之前处理 Windows Terminal 下子进程弹窗问题时，就吃过「Session 0 隔离」和「父进程 console 句柄继承」的亏。**Agent 驱动场景天然需要用户会话上下文，服务模式是逆着需求走的。**

**推荐方案（任务计划程序）配置要点：**

```
触发器：登录时（At log on）
   └─ 用户空闲/唤醒时也补一个触发器，防休眠后不恢复
操作：  启动 node.exe（用绝对路径）
   ├─ 程序: C:\...\node.exe
   ├─ 参数: C:\...\uni-terminal\server.js
   └─ 起始于: C:\...\uni-terminal      ← ⚠️ 必须填，否则相对路径全错
条件：  □ 只有在计算机使用交流电源时才启动（要取消勾选，笔记本电池也要跑）
设置：  ☑ 如果任务失败，每 1 分钟重启一次，最多 3 次   ← 崩溃自愈
        ☑ 如果任务已在运行，则不启动新实例
        □ 如果任务运行时间超过…则停止（要取消勾选）
账户：  你自己的账户，勾选「不管用户是否登录都要运行」（需要存密码）
```

**另外做两件事：**

1. **提供一个 CLI 安装命令**：`uni-terminal install-service` —— 自动生成并注册计划任务（用 `schtasks /Create`）。**不要写 `.ps1` / `.bat` 脚本文件**（中文路径会有编码问题），直接用 Node 调 `schtasks`，参数走数组传递。
2. **做一个托盘图标**（可选）：显示"服务运行中 / 有 N 台设备连接"，并提供「暂停接受连接」的开关 —— 对应文档 01 里说的「正在被谁控制」的可见性。

### 3.4 手机怎么找到服务：三级寻址降级

这是你问题的核心："手机拿着凭证去找这个服务口"。**答案是三级降级：**

```
手机打开 PWA
   │
   ├─ ① 试试「上次已知地址」（存在 IndexedDB，非敏感→不受 ITP 影响）
   │     成功 → 直接连
   │     失败 ↓
   │
   ├─ ② 局域网探测（如果当前在同一个 WiFi）
   │     ├─ 监听电脑的 mDNS / UDP 广播（广播包里带 IP:port 明文）
   │     └─ 或直接探测之前记录的局域网 IP
   │     成功 → 连上，并把新地址存进 ①
   │     失败 ↓
   │
   └─ ③ 外网兜底地址（配置的固定隧道域名）
         成功 → 连上
         失败 → 显示"找不到你的电脑"+ 排查提示
```

**⚠️ 一个关键细节：mDNS 在 iOS 上不能解析，但广播可以用。**

iOS Safari **不能解析 `.local` 域名**（比如 `mymac.local`），但**可以接收 UDP 广播包**。所以：

> **不要**广播一个域名让手机去解析。
> **要**在广播包里**直接带 IP:port 明文**，手机收到后直接用 IP 连。

```js
// 电脑端广播（用 multicast-dns）
{
  service: 'uni-terminal',
  port: 8787,
  addresses: ['192.168.1.23'],     // ← 明文 IP，别让手机去解析域名
  version: '1.0.0',
  deviceId: 'desktop-main'
}

// 手机端（WebSocket 探测，不需要 mDNS 库）
// 拿到候选 IP 后，逐个尝试 ws://<ip>:8787/ws?probe=1
```

**如果懒得做广播**（MVP 阶段）：配对时把局域网 IP 记下来，然后**在路由器上做 DHCP 保留**（静态租约），IP 就不会变。这是最省事的路子。

**还有一个更巧的做法**：配对时手机从**服务端拿到的响应里就带上地址簿**，形如：

```json
{
  "deviceId": "desktop-main",
  "addresses": [
    { "type": "lan",        "url": "ws://192.168.1.23:8787", "ttl": 3600 },
    { "type": "tunnel",     "url": "wss://uni.example.com",  "ttl": 0 }
  ]
}
```
手机按顺序试，谁通用谁。**`ttl: 0` 表示"永久有效"**，`ttl` 是秒数表示"这个地址可能过期，过期后要重新探测"。

### 3.5 完整时序：从开机到手机重连

```
【电脑端】
  开机 → 任务计划程序启动 daemon
       → 读 SQLite 设备表（知道有哪几台手机被授权过）
       → 监听 :8787（局域网） + 启动 cloudflared（外网模式）
       → 向隧道域名注册（隧道自带固定域名，无需会合服务器）
       → 开始广播 mDNS 包（局域网模式）

【手机端】
  从桌面点开 PWA（无需扫码）
       → 浏览器自动带上 L2 httpOnly Cookie
       → 按 ①②③ 顺序尝试连接
       → 服务端校验 L2（存在？未吊销？未过期？）
       → 下发 L3（15 分钟，存内存）
       → WebSocket 建立，带 lastEventId 请求补齐断档事件
       → 进入控制台

【例行】
  L3 到期前 2 分钟 → 用 L2 静默换新 L3
  每次换 L3 → 顺带刷新 L2 Cookie 的 Max-Age（滑动续期）
  每 30~60 秒 → WebSocket 心跳（⚠️ 见 4.4，隧道会掐空闲连接）

【吊销】
  桌面端删设备 → 服务端标记失效 → 主动断开该设备的 WebSocket
              → 手机收到 close 码 → 清本地状态 → 回配对页
```

## 4. 传输层定案

### 4.1 推荐：分层默认（这是最终答案）

| 场景 | 频率 | 方案 | 手机要装东西 | 成本 |
|---|---|---|---|---|
| **S1 在家（同 WiFi）** | **最高频** | **`lan` 局域网直连** | ❌ 什么都不装 | **零** |
| **S2 在外（首选）** | 次高频 | **`cloudflare` 隧道** | ❌ 纯浏览器 | **一个域名（约 ¥30/年）** |
| S2 在外（进阶） | — | `easytier` 组网 | ✅ EasyTier | 域名 + 装个通用工具 |
| S3 分享给他人 | 少见 | 同 S2 | ❌ | 同上 |
| 逃生舱 | — | `manual` 填任意 URL | — | — |

**为什么这个排序（三条理由）**：

1. **`lan` 覆盖最高频场景且零配置** —— 沙发上用手机控制书房电脑，这是 70%+ 的使用场景，不需要任何网络设置。**默认必须是零配置的**，这是"便捷性"的第一层答案。
2. **`cloudflare` 与「扫码即用不装 App」的产品定位完全一致** —— 手机纯浏览器，这是对 Happy「必须装专用 App」的直接反击。如果外网方案要求装东西，这个定位就崩了。
3. **`easytier` 作为进阶选项保留** —— 给在意延迟和隐私的人。它是**通用组网工具**（装了还能连 NAS），性质与"必须装 Happy"不同。

### 4.2 为什么外网首选 Cloudflare Tunnel

**决定性优势：它不需要任何自己的服务器。**

| 项 | Cloudflare Tunnel |
|---|---|
| 需要公网 IP | ❌ 不需要 |
| 需要 VPS | ❌ 不需要 |
| 需要备案 | ❌ 不需要 |
| 需要域名 | ✅ **需要（唯一门槛，约 ¥30/年）** |
| HTTPS | ✅ 自动 |
| 限速 | ✅ **官方免费不限速** |
| DDoS 防护 | ✅ 自带 |
| 运维 | ✅ 零（`cloudflared` 主动出站连 CF，不受家用防火墙影响） |

**原理**：`cloudflared` 从你的电脑**主动向 CF 边缘建立一条出站隧道** → 外部请求先到 CF → CF 顺着隧道反向代理回你的服务。所以家里不用开任何入站端口。

**⚠️ 必须知道的三个代价**：

1. **CF 在边缘解密流量**（这是它 WAF / 缓存能力的前提）→ 你的代码、对话、diff 对 CF 是明文 → **要保住隐私必须叠加应用层 E2E**（对应文档 01 的 6.5 密钥交换预留）。
2. **国内走境外节点**（香港/新加坡/美国），延迟几十到上百 ms，晚高峰有跨境拥堵。对"事件流 + diff + 日志"这点数据量完全够（已核实），但**不适合传大文件**。
3. **官方明说免费隧道没有 SLA、仅供测试开发**。自用完全可以，但别拿它做商业服务。

**`cloudflared` 的常驻**：装好后可以 `cloudflared service install` 注册成 Windows 服务。它和我们的 daemon 是两件独立的事，但可以在同一个安装流程里一起管。

### 4.3 新发现：`trycloudflare.com` 零门槛试玩通道

**这是本轮调研的一个意外收获，对开源项目很有价值：**

```
cloudflared tunnel --url http://localhost:8787
```

**这条命令不需要登录、不需要域名、不需要任何配置**，几秒后直接给你一个 `https://xxx-yyy.trycloudflare.com` 地址，自带 HTTPS。

**优点**：真正做到"零门槛" —— 用户 `git clone` 完就能体验外网访问，不用先买域名。
**缺点**：**域名随机且每次重启都变**（所以不能用于长期使用）。

**产品化的用法**：
> 首次启动时，如果检测到用户**没有配置域名** → 提议"要不要用临时通道试一下？" → 用快速隧道拿到一个随机地址给手机连。
> 同时明确提示：「这是临时地址，重启后会变。要长期使用，配置一个域名即可固定。」

**这个设计对开源项目很重要** —— 把"要先买域名"这个心理门槛从"第一次体验"推迟到"决定长期使用"。转化率差别很大。

### 4.4 ⚠️ 实操细节：WebSocket 必须做心跳保活

**这条不做的话，外网模式下会出现"用一会儿就断"的间歇性故障，而且极难排查。**

原因：中间节点（CF 边缘、家用路由器 NAT、运营商）会**回收长时间没有数据的 TCP 连接**。我们的场景恰恰是"连接长时间空闲"——Agent 在跑一个 5 分钟的任务，中间没有任何事件推送。

**做法**：

```js
// 客户端 & 服务端双向心跳
const HEARTBEAT_INTERVAL = 30_000;   // 30 秒，远小于各层超时（通常 60~100 秒）

setInterval(() => {
  if (ws.readyState === WebSocket.OPEN) {
    ws.send(JSON.stringify({ type: 'ping', t: Date.now() }));
  }
}, HEARTBEAT_INTERVAL);

// 双向超时检测：连续 2 次心跳没有回应 → 判定连接已死 → 主动重连
```

**同时要做的事**：
- **服务端定期清理僵尸连接**（不能只依赖 TCP 的 FIN，很多情况下收不到）
- **重连要带 `lastEventId`**，让服务端补齐断档事件（这条在文档 01 已作为硬需求）
- **重连要指数退避**（1s → 2s → 4s → 8s，上限 30s），避免手机电梯里进进出出时疯狂重连

### 4.5 隐私判断：先跑通，再上 E2E

**我的建议：v1 走 CF 隧道时先不做 E2E 数据加密，但配对时的密钥交换必须做进去。**

理由：
1. **代价 vs 收益** —— v1 阶段你连的都是自己的机器、自己的代码在自用。CF 可见明文的实际风险远低于"做不完 E2E 导致项目停摆"。
2. **迁移路径是通的** —— 只要配对时做了密钥交换（手机生成 X25519 密钥对、服务端转交加密载荷，约 30 行），v2 加数据加密时**不需要重新配对**。这是文档 01 就定下来的架构决定。
3. **想立刻要隐私的人走 `easytier`** —— EasyTier 是真端到端（点对点直连率 60%+），根本不经第三方。

**证伪一下这个判断**：如果哪天你发现自己在手机上跑的是**公司的代码**或者**有敏感数据的项目**，那 E2E 就要提到 v1。这个标准很清楚，你可以自己判断。

### 4.6 产品化的自动探测逻辑

不要替用户做选择，而是**探测 + 给结论 + 一键配置**：

```
启动时自检：
  ├─ 能拿到局域网 IP 吗？            → 是：`lan` 模式立即可用（零配置，默认开）
  ├─ 有公网 IPv6 吗？                → 是：提示"可以走 IPv6 直连（延迟最低）"
  ├─ 配了域名 + cloudflared 吗？      → 是：`cloudflare` 模式可用
  ├─ 装了 EasyTier 吗？              → 是：`easytier` 模式可用
  └─ 以上都没有？
       → 提示："要出门在外也能用，选一个："
          A. 临时试一下（trycloudflare，零门槛，地址会变）   ← 降低首次体验门槛
          B. 长期使用（需要域名，约 ¥30/年）                ← 说明为什么值得
          C. 我有自己的方案（manual，填任意 URL）
```

**这个自检页要做得像"网络诊断"，而不是"配置表单"** —— 用户看到的是"当前可用：局域网 ✅｜外网 ❌ 需要配置"，而不是一堆协议名让他选。

## 5. 更新后的 MVP 范围

**基于以上分析，原 MVP 清单要加两件事、砍一件事：**

| 变更 | 项 | 原因 |
|---|---|---|
| ➕ **加** | **微信/QQ 拦截遮罩** | 不做的话，国内用户第一个扫码就废了。**优先级等同核心链路** |
| ➕ **加** | **Chromium 一键安装按钮 + iOS 引导页** | 否则"扫码即用"不成立 —— 用户每次都要手动输地址 |

| ⏸ **延后** | E2E 数据加密 | 保持不变（但配对时预留密钥交换） |

### 修订后的验证清单

```
安装与引导链路（新增）
[ ] Android Chrome 扫码 → 出现「装到桌面」按钮 → 点击 → 真的装上

配对码加固（新增）

常驻与重连
[ ] 重启电脑 → daemon 自动起来（任务计划程序生效）

传输
[ ] 局域网：手机连 WiFi 打开 PWA → 直连成功，延迟 < 5ms

```

### 明确不在 MVP 范围

- ❌ mDNS 自动发现（用固定 IP + DHCP 保留替代）
- ❌ EasyTier / IPv6 / frp 适配器（接口留好，只实现 `lan` + 可选 `cloudflare`）
- ❌ E2E 数据加密（配对预留密钥交换）
- ❌ PTY 兜底通道、多 Agent、多用户
