**最直接的竞品是 `slopus/happy`（23.7k★，MIT）** —— 它已经实现了"手机上控制家里电脑的 Claude Code"这件事，有端到端加密、推送通知、语音交互。它今天还在活跃推送。

### Happy 的四个明确短板（= 你的机会）

1. **只支持 Claude Code 和 Codex 两个 Agent**（README 明示）。你要管的其他工具它一个都不管。
2. **必须装 App** —— iOS / Android / macOS 原生应用，扫码开浏览器这条路它没走。
3. **强依赖官方 relay 服务器**（Happy Server）。虽然端到端加密，但你的会话元数据要过第三方。**自托管选项不是默认路径。**
4. **1012 个 open issues** —— 需求堆积严重，说明扩展速度跟不上。

### 其他项目的共同盲区

- **`claudecodeui` 是 AGPL-3.0** —— 传染性许可，你参考架构可以，**照抄代码会强迫你的项目也 AGPL**。
- **所有项目都只覆盖 1~3 个 Agent**，且都是**为具体 CLI 写死适配器**（在 ACP 普及前设计的）。
- **没有一个是"扫码即用"** —— 要么装 App，要么 Tailscale，要么配 SSH。
- **清一色 macOS/Linux 优先**，Windows 是被忽略的一侧。

## 二、核心洞察：ACP 是代际差异，不是功能差异

这是本轮调研最重要的发现。`acpx` 官方文档列出了**内置支持的 22 个 Agent**：

| 类别 | Agent |
|------|-------|
| **国际主流** | Claude Code、Codex、Gemini CLI、Cursor、GitHub Copilot CLI、Factory Droid、OpenCode、Grok Build、Poolside、Kiro、Kilocode、Mux、Pi、fast-agent |
| **国产/中文生态** | **Kimi CLI、Qwen Code、iFlow、Qoder、Trae、MiniMax Code (mcode)**、ZeroClaw |

每个 Agent 支持**完全一致的命令面**：

```bash
acpx <agent> prompt [...]          # 发指令
acpx <agent> exec [...]            # 一次性运行
acpx <agent> cancel                # 取消
acpx <agent> set-mode <mode>       # 切换模式
acpx <agent> status
acpx <agent> sessions list|new|ensure|close|show|history|prune
```

**这意味着什么：**

> 现有竞品（Happy / claudecodeui / CodePilot）在 ACP 成熟前，为每个 CLI 手写适配器，所以只能覆盖 1~3 个工具，且每家 CLI 更新都要跟着改。
>
> **你走 ACP，一次性覆盖 22 个，且未来新增的 ACP agent 零成本接入。** 这是一个**结构性优势**，不是"多支持几个工具"的功能优势。

而且 acpx 是 **MIT + TypeScript + 导出可嵌入 SDK（`acpx/runtime`、`acpx/flows`）**，还在文档里明确处理了 Windows 下的 `claude.exe` 解析。**它天生就是为被你的后端调用而设计的。**

### ACP 覆盖不到的两个（诚实告知）

| 产品 | ACP 支持 | 能否纳管 | 方案 |
|------|---------|---------|------|
| **小米 MiMo Code** | ❌ README 无 ACP（只有自有的 `mimo serve`/`attach`） | ⚠️ 可 | 它是终端 TUI，**走 PTY 兜底通道** |
| **ZCode 桌面版** | ❌ 桌面 GUI 应用 | ❌ 一期不行 | 只能等官方 CLI，或远期做 OS 级 UI 桥接 |

**结论：你原始诉求里的"纳管 ZCode"，一期做不到。** 这不是技术选择问题，是它没有开放接口。需要你接受这个现实或调整期望。

## 三、修正：herdr 从"推荐核心"降级为"可选后端"

第一轮我把 herdr 列为最值得复用的项目。**深挖后我要收回这个推荐**，理由如下（都是官方文档明确的）：

| # | 问题 | 官方原文/事实 | 对你的影响 |
|---|------|--------------|-----------|
| 1 | **Windows 不能做远程目标主机** | "Windows as a `herdr --remote` target host — **unsupported**" | 你的开发机正是 Windows，远程接入这条主路直接断了 |
| 2 | **Windows 不支持 terminal attach** | "Direct terminal attach (`herdr terminal attach`) — **unsupported**" | 无法用它把终端流转给 Web |
| 3 | **pane 内容是文本快照，不是字节流** | `pane.read` 的 source 为 `visible`/`recent`/`detection` | **无法喂给 xterm.js 做真终端渲染**（会丢 ANSI 精细状态、高频刷新性能差） |
| 4 | **无鉴权** | 文档"未提及任何鉴权机制"，依赖 OS 文件权限 | 你要自己补一层，等于白送的工作量 |
| 5 | **架构阻抗** | 它是给人用的 TUI，不是 Web 后端组件 | 把它降级成后端，形态错配 |
| 6 | **它最核心的能力被 ACP 覆盖** | 状态检测靠"进程名匹配 + 终端输出启发式" | **走 ACP 后，状态由协议主动上报，不需要猜。** 这是 ACP 的本质优势 |

补充事实：herdr 的 Windows 支持其实已经 **GA**（不再是 beta），支持 ConPTY 原生 pane、`--remote` 连 Linux/macOS、插件（preview）。**中文 IME 锚点仍是 partial**（对你有实际影响）。它依然是个优秀的工具 —— **但它是"给人用的终端"，不是"给 Web 用的运行时"。**

**herdr 的正确定位：**
- ① **竞品参照**：它的 agent 状态启发式检测、State/Runtime 分离架构、CJK IME 处理都值得读
- ② **可选的"高级后端"**：如果将来要做"在真实终端里编排多 Agent"，可以把 herdr 的 session 当作一个特殊 Agent 纳管
- ③ **不要**作为一期核心依赖

## 四、修正后的推荐方案

### 一句话定位

> **一个扫描即用的自托管 Web 控制台，通过 ACP 协议统一纳管 22+ 个 AI 编程 Agent，不装 App、不经第三方中继、Windows 优先。**

### 差异化三角（每一条都对着竞品的具体短板）

| 你的点 | 打的是谁 | 为什么成立 |
|--------|---------|-----------|
| **ACP 原生，22+ Agent 全覆盖** | Happy 只 2 个、claudecodeui 只 3 个 | 结构性优势，非功能优势 |
| **扫码即用 + 纯自托管** | Happy 要装 App + 过官方 relay | 你不需要中继服务器，会话不出你的机器 |
| **Windows 优先** | 所有竞品都是 macOS/Linux 假设 | 你就用 Windows 11 开发，dogfooding 最真实 |

### 技术选型（明确答案）

| 层 | 选型 | 理由 |
|----|------|------|
| **统一接入** | **acpx**（MIT） | 22 个内置 Agent + `--agent` 逃生舱 + NDJSON 事件流 + 可嵌入 SDK。**没有第二个选择能比。** |
| **通用终端兜底** | **node-pty + xterm.js** | 覆盖没有 ACP 的 TUI 工具（如 MiMo Code）；Windows 下走 ConPTY，成熟 |
| **服务端** | **Node.js 22 + TypeScript**（Hono/Fastify + ws） | 与 acpx 同生态，可直接 `import` 它的 runtime |
| **持久化** | **SQLite**（WAL） | 单文件零运维，你是单人维护 |
| **扫码配对** | **自研**（短时效 Token + 一次性 + 可吊销 + 权限域限定） | ZCode 的安全债就是你的卖点 |
| **前端** | **React + xterm.js**，做成 **PWA** | 可装到手机桌面 + 支持推送，**又不用上架应用商店** —— 这是对 Happy"必须装 App"的直接反击 |

### 明确不采用

- ❌ **herdr** 作为一期核心（理由见上）
- ❌ **OpenHands**（87k★）—— 它的定位是"自己的 Agent runtime"，你要的是"纳管已有 Agent"，用法错配；且 Rust 代码库定制成本高
- ❌ **抄 claudecodeui 的代码**（AGPL-3.0 传染），只参考架构

## 五、待讨论的问题（需要你的判断）

### Q1. 自用场景下，"不可替代性"是否成立？（最重要）

诚实地说：**如果只是自用 Claude Code，装个 Happy 就够了**，你不需要写一行代码。

你要自己做，价值必须来自这几个之一：
- 你想管的工具 Happy 不管（Kimi/Qwen/iflow/Trae/ZCode…）
- 你不想让会话过第三方服务器
- 你想要"扫码开浏览器"而不是"装 App"
- 你想通过做这个项目学 ACP/PTY/WebSocket
- 开源本身有社区价值

**请确认你的真实动机排序** —— 这直接决定方案该往哪个方向优化。如果核心动机是"学技术 + 掌控"，那 MVP 可以做得很薄；如果是"要一个比 Happy 更好的日常工具"，那要重点打磨移动端体验。

### Q2. 一期范围：先单 Agent 闭环，还是直接上 acpx 多 Agent？

- **A（推荐）**：先做 **Claude Code 单 Agent + 扫码 + Web 终端** 最小闭环。因为真正的技术风险在**"扫码链路"和"PTY 字节流跨进程/跨网络到浏览器"**这两处，不在 Agent 调度。1~2 天能验证。
- **B**：直接上 acpx 多 Agent。省事，但如果扫码/字节流有问题，会分不清是哪层的锅。

### Q3. 许可协议选哪个？

- **MIT**（推荐）：最大化传播，与你复用的 acpx(MIT)/xterm.js(MIT) 一致
- **AGPL-3.0**：防止别人拿去做闭源 SaaS，但会吓跑一部分使用者

**注意**：只要参考了 claudecodeui 的代码，你就**必须** AGPL。建议只看架构、不抄代码，保持 MIT 自由。

### Q4. 手机端形态？

- **响应式 Web**（最简单，扫码即用）
- **PWA**（推荐）：能装桌面 + 推送通知，不用上架
- **原生 App**：不推荐，单人维护三端成本过高

### Q5. 要不要保留"真实终端视图"？

- **ACP 路线给的是结构化事件**（工具调用、diff、思考过程），**这比终端画面更适合手机**，也是 CodePilot/Companion 的做法。
- 但通用兜底（MiMo Code 这类无 ACP 的 TUI）**必须有终端视图**。

**建议：两种视图都给，默认展示结构化任务视图，终端作为"细节"折叠面板。** 这也正好体现了双通道架构。

## 六、下一步建议

**第一步（今天就能做）**：在你的 Windows 上跑通扫码链路的最小验证

```
node-pty 开一个 shell → WebSocket 推字节流 → 浏览器 xterm.js 渲染 → 手机扫码打开
```

这条链路通了，整个项目就没有未知的技术风险了。**其余全是组装工作。**

**第二步**：接入 acpx，跑 `acpx claude "..."` 确认 NDJSON 事件流够不够撑起 UI。

**第三步**：把第一步和第二步缝起来 —— 这正是 Uni-terminal 的核心。
